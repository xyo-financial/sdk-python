## 🏗 1. Two-Layer Architecture

The codebase strictly enforces a two-layer separation of concerns:

```
┌────────────────────────────────────────────────────────┐
│                    xyo (Facade)                        │
│  - Client (Sync) & AsyncClient (Async)                 │
│  - Type annotations (PEP 484, PEP 561 py.typed)        │
│  - Memory-Safe In-Memory & Streaming GZip & Tar Reader │
│  - Zero-Trust Egress Domain Validation & SSRF Defense  │
│  - RFC 7807 Typed Exception Hierarchy                  │
└───────────────────────────┬────────────────────────────┘
                            │ wraps / references
┌───────────────────────────▼────────────────────────────┐
│              xyo._generated (Transport)                │
│  - Low-level OpenAPI Python Models & API stubs         │
│  - Machine-generated by OpenAPI Generator (httpx)      │
└────────────────────────────────────────────────────────┘
```

> [!IMPORTANT]
> **Never modify files inside `src/xyo/_generated/` manually.** All changes to API contracts, models, or endpoint stubs must originate from the central specification repository (`xyo-financial/specs`). Linters (`ruff`, `mypy`) are configured to ignore `_generated`.

## 🔀 2. Contribution Workflow & Decision Matrix

| Nature of Change | Target Location | Process |
| :--- | :--- | :--- |
| **API Contract / Endpoint / Schema** | `xyo-financial/specs` | Open PR in specs repository &rarr; triggers automated regeneration workflow in `sdk-python`. |
| **Ergonomics / Async / Streaming / Security** | `src/xyo/` | Open PR in `sdk-python` with accompanying pytest coverage. |
| **Bug Fix in Wrapper Logic** | `src/xyo/` | Submit PR with regression unit test in `tests/`. |

## ⚙️ 3. Automated & Local Code Generation

### 🔹 Automated Regeneration (CI/CD)
When an OpenAPI spec is tagged in `xyo-financial/specs`, GitHub Actions dispatches a `spec_tagged` event to `.github/workflows/generate.yml`, regenerating `src/xyo/_generated/`, running the test suite, and creating a pull request or commit.

### 🔹 Local Regeneration
To regenerate the client locally against a local checkout of specs:

```bash
make generate
```

---

### 📋 Generated Code Policy

> [!IMPORTANT]
> `src/xyo/_generated/` is produced by OpenAPI Generator and is committed **exactly as the generator emits it**.

- **Never edit it by hand.** Any manual change is silently destroyed by the next specification dispatch. Real fixes have already been lost this way elsewhere in the fleet, including a privacy fix in `sdk-go` that suppressed request bodies in debug logs, and a Maven parent block in `sdk-java`.
- **Never reformat it.** It is excluded from ruff, mypy and coverage via `pyproject.toml`. Generated output that has been reformatted no longer matches what the generator produces, so every regeneration then fights CI and the diff fills with style churn instead of specification changes.
- **It is out of scope for code review, security review, audit and any other sanitisation pass.** Do not raise findings against generated output. Review the specification in [`xyo-financial/specs`](https://github.com/xyo-financial/specs) or the hand-written wrapper instead, which is what consumers actually call.
- **It carries no hand-written tests.** Generated tests are disabled at generation time. Test the wrapper.
- **Its dependencies are runtime dependencies.** The generated client is published in the wheel, so `pydantic`, `python-dateutil` and `typing-extensions` are declared in `[project.dependencies]`. Do not remove them.

If generated output is wrong, fix it at source, never in the output:

1. Change the specification upstream in `xyo-financial/specs`, if the contract itself is wrong.
2. Change the generator invocation in `.github/workflows/generate.yml`, if it is a generation setting.
3. Add the file to `src/xyo/_generated/.openapi-generator-ignore`, if the generator's version of it is genuinely not the source of truth.

### 🔹 How the Wrapper Uses the Generated Layer

The hand-written wrapper in `src/xyo/` is the public API. It does not restate the wire contract: `models.py` parses and serialises through the generated pydantic models via `from_generated()` and `to_generated()`, so field names, casing and types come from the specification.

The wrapper exists to add what the generator does not provide: a sync client alongside the async one, in-memory gzip and tar streaming, zero-trust egress and SSRF validation, an RFC 7807 typed exception hierarchy, and ergonomic accessors. Add capability there; never in `_generated/`.

## 🛠 4. Prerequisites & Development Environment

- **Python:** Python 3.9+ (`python --version` >= 3.9.0)
- **Tooling:** `pytest`, `pytest-asyncio`, `respx`, `ruff`, `mypy`
- **Docker:** (Optional) Docker for containerized verification

---

## 🛡 5. Quality Gates & Validation

Before submitting a Pull Request, ensure all local verification checks pass:

```bash
# 🤝 Run test suite with coverage
pytest

# 🤝 Run linter and formatting check
ruff check .
ruff format --check .

# 🤝 Run type checker
mypy src/xyo
```

Or run via Docker:

```bash
make docker-test
```

---

## 🧪 6. Development & Testing Guide

- **Unit Tests:** Located in `tests/`. Use `respx` to simulate HTTP responses deterministically without requiring a live server.
- **Coverage Target:** Minimum **90% branch and statement coverage** for all files in `src/xyo/` (excluding `_generated`).
- **Security Tests:** Ensure any new URL or header inputs have explicit SSRF, CRLF, and bounded buffer tests.

---

## 🚀 7. Pull Request & Commit Standards

- **Conventional Commits:** Use standard prefixes:
  - `feat(client): add support for bulk batch streaming`
  - `fix(security): sanitize CRLF characters in x-api-user header`
  - `docs(readme): add FastAPI async example`
  - `test(tar): add decompression bomb test fixture`
- **Branch Naming:** `feat/feature-name`, `fix/issue-description`, `docs/update-policy`.

---

## 📦 8. Release & Versioning Process

The project adheres to [Semantic Versioning 2.0.0](https://semver.org/):
- **Patch (v2.0.x):** Bug fixes, security patches, internal refactorings.
- **Minor (v2.x.0):** Backwards-compatible public API additions.
- **Major (vX.0.0):** Breaking public API changes.

Publishing to PyPI is triggered automatically when a Git tag adhering to `v[0-9]+.[0-9]+.[0-9]+` is pushed to `main`.
